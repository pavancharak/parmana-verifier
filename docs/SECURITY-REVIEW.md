# Security review scope: parmana-verifier 0.2.0

This document is for an external reviewer. It lists what the verifier is meant to do, what to examine, and how to run it. The verifier is an offline checker for Parmana Execution Trust Records. It does not sign, send, or call any service.

## What the verifier claims

For a record passed to `verifyExecutionTrustRecord(record, trustKeys)`:

1. `trustRecordHash` equals the SHA-256 of the canonical JSON of the record's signed fields.
2. The legacy `signature` verifies over that canonical JSON with a key from the trust set.
3. If a `signatures` array is present, it has at least two entries with distinct algorithms, and each verifies over the canonical JSON plus `schemaVersion`. The verifier refuses duplicate algorithms and unsupported algorithms.
4. A key is used only if the trust set pins it. A key is pinned by the SHA-256 fingerprint of its public key (`src/trust.mjs`). A key is accepted only when:
   - it is not marked `compromised`;
   - the record's `createdAt` falls within `[validFrom, validUntil)`;
   - its algorithm matches the signature entry.

The verifier makes no network calls and has no runtime dependencies. It depends on Node 24 with OpenSSL 3.5 or newer for ML-DSA-65 (`dilithium3`).

## In scope

- `src/canonical.mjs`: canonical JSON serialization. Look for inputs that serialize differently from what was signed.
- `src/verify.mjs`: the checks above, the commitment rule for messages over 4096 bytes, and the handling of malformed input.
- `src/trust.mjs`: trust-set parsing and key pinning, including validity windows, the compromised flag, and fingerprint checks.
- `bin/parmana-verify.mjs`: the command-line wrapper and how it reads files.
- Test vectors in `test/vectors/`, and whether the tests catch tampering.

## Out of scope

- The Parmana service that produces records and signatures (a separate private repository).
- Key generation, storage, and rotation, which happen in that service.
- Whether a trust set is correct. The verifier trusts whatever keys the trust set pins; deciding which keys to pin is the operator's responsibility.

## Questions for the reviewer

1. Can any record pass verification after a field is changed, including fields outside the signed set?
2. Can a key outside the trust set, a key past its validity window, or a compromised key be accepted?
3. Can the hybrid check be satisfied by two entries that use one key or one algorithm?
4. Do malformed inputs (wrong types, prototype keys, very large inputs, invalid base64 or PEM) cause a crash that stops a check, rather than a refusal?
5. Does the command-line tool report a valid result for a file it did not fully read?

## How to run it

```sh
npm test
npm run examples
```

Both run on Node 24 or newer.

## Known limits

- Verification depends on the trust set supplied by the caller. The verifier cannot tell whether a pinned key belongs to Parmana.
- The verifier does not check revocation beyond the `compromised` flag and the validity window.
- The test vectors were generated by the Parmana service and checked against its signing code. They are not an independent specification.
